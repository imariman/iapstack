# v0.1.0 Huawei Sandbox Release Gate

IAPStack v0.1.0 remains a release candidate until this runbook has been completed
against one immutable commit on a real Huawei device. The automated Compose fixture is
necessary, but it cannot replace provider-managed account, billing, renewal, refund,
revocation, and notification behavior.

The operator must not record application keys, Huawei credentials, signed purchase
data, signatures, purchase tokens, customer identifiers, notification bodies, webhook
secrets, or database ciphertext in the evidence file. Request IDs are the only allowed
link from this record to protected operational logs.

## Authoritative references

- [Huawei sandbox testing](https://developer.huawei.com/consumer/en/doc/hmscore-guides/sandbox-testing-0000001050035039)
- [Huawei subscription functions and sandbox renewal timing](https://developer.huawei.com/consumer/en/doc/HMS-Plugin-Guides-V1/subscription-func-0000001126667693-V1)
- [Huawei `InAppPurchaseData` lifecycle fields](https://developer.huawei.com/consumer/en/doc/HMSCore-References/inapppurchasedata-0000001050137635)
- [Huawei subscription fee refund behavior](https://developer.huawei.com/consumer/en/doc/hmscore-guides/refund-subscription-fee-0000001050033084)

Recheck these pages immediately before execution. If current provider behavior or
documentation differs from this runbook, stop the release and update the adapter,
tests, and runbook together.

## 1. Freeze and validate the candidate

Record the exact candidate commit. Do not test a dirty worktree.

```sh
git status --short
git rev-parse HEAD
go test -race -count=1 ./...
./deploy/e2e/run.sh
```

Wait for the candidate commit's GitHub CI run to pass the Go, Flutter, container, and
Compose jobs. Copy the example evidence to the untracked release record and replace
every placeholder:

```sh
cp docs/releases/v0.1.0-sandbox-evidence.example.json \
  docs/releases/v0.1.0-sandbox-evidence.json
```

Set `commit` to the candidate SHA and `ci_run_url` to that exact immutable workflow
run. Leave every result `false` until the corresponding assertion has been observed.

## 2. Confirm the sandbox boundary

1. Register the exact application package, signing certificate, and build version in
   AppGallery Connect. Configure one non-consumable lifetime product and one monthly
   subscription for the application mapped in IAPStack.
2. Add the signed-in HUAWEI ID as a sandbox tester and allow provider configuration
   changes time to propagate.
3. Install the candidate APK on a real Huawei device with current HMS Core and launch
   the Flutter harness described in the example README.
4. Verify that the harness reports both `Test account: Eligible` and
   `Sandbox APK: Eligible`. Record the non-secret application, APK, device, and HMS
   Core versions. Stop immediately if either condition is not eligible or if Huawei's
   checkout does not display its sandbox notice; a real charge may otherwise occur.

For subscription timing, Huawei documents these sandbox mappings: one week to three
minutes, one month to five minutes, two months to ten minutes, three months to fifteen
minutes, six months to thirty minutes, and one year to one hour. A sandbox subscription
auto-renews at most six times. Use a fresh tester/product state when a scenario needs a
new lifecycle.

## 3. Execute lifecycle scenarios

Record the UTC observation time, every distinct IAPStack request ID, and a concise
assertion for each scenario. Confirm both the entitlement snapshot and the durable
webhook/event count; a successful HTTP response alone is insufficient.

| Evidence scenario | Required observation |
| --- | --- |
| `lifetime_purchase` | One valid lifetime purchase grants access and creates one logical entitlement transition and webhook event. |
| `lifetime_duplicate_restore` | Two restore submissions preserve the same access, projection version, and logical event count. |
| `subscription_initial` | The initial purchase is active, grants access, and reports automatic renewal enabled. |
| `subscription_renewal` | One compressed renewal advances the authoritative validity period and creates exactly one new logical transition. |
| `subscription_cancellation` | Stopping renewal records canceled-at-period-end while access remains allowed until expiration. `cancellationTime` must not be treated as immediate revocation. |
| `subscription_expiration` | After the final validity period, authoritative reconciliation denies access as expired. |
| `subscription_grace` | A provider-created grace state keeps access allowed only through `graceExpirationTime`; record the authoritative fields observed. |
| `subscription_refund` | Refunding only the latest subscription fee keeps access and renewal behavior described by Huawei. If the observed authoritative response differs, stop and investigate rather than rewriting the assertion. |
| `subscription_revocation` | Revocation produces `cancelTime`, immediately denies access, and creates one revocation transition. |
| `invalid_signature` | Tampered signed data returns a stable rejection and creates no observation, entitlement change, or outbox event. |
| `wrong_application_binding` | Valid evidence submitted to another application scope is rejected without a write. |
| `wrong_product_binding` | A mismatched claimed product is rejected without a write. |
| `wrong_customer_binding` | A customer different from signed `developerPayload` is rejected without a write. |
| `duplicate_notification` | Two submissions of the same signed notification produce one inbox identity and no duplicate transition or webhook event. |
| `missed_notification_reconciliation` | With notification delivery intentionally omitted, scheduled authoritative reconciliation converges to the correct entitlement exactly once. |

Negative requests may be constructed only in an ephemeral operator session. Never put
the source purchase body or signature into the evidence record, shell history, CI
output, issue tracker, or pull request.

Huawei distinguishes three related subscription outcomes. `cancellationTime` stops the
next renewal but retains service through the current period. `cancelTime` means the
receipt was revoked and service ends immediately. The server-side fee-refund operation
alone does not cancel or revoke the subscription; test refund and revocation as separate
scenarios.

## 4. Verify the production webhook receiver

Use the exact receiver implementation and replay window intended for production:

1. Verify HMAC-SHA-256 over `<unix_timestamp>.<exact_raw_body>` and accept the valid
   delivery.
2. Change one raw body byte while retaining the headers and confirm rejection.
3. Submit a correctly signed event outside the configured timestamp tolerance and
   confirm rejection.
4. Replay an accepted event ID and confirm the receiver applies its effect only once.

Mark the four `webhook` assertions only after checking receiver state, not merely its
HTTP response.

## 5. Validate and promote

Set `no_secrets_attested` only after reviewing the entire JSON file. Validate the
closed evidence contract:

```sh
go run ./cmd/iapstack-release \
  docs/releases/v0.1.0-sandbox-evidence.json
```

The validator rejects unknown fields, incomplete CI or sandbox checks, missing or
failed scenarios, reused/invalid request IDs, incomplete webhook controls, unstable
version names, and missing secret attestation.

Open a release-evidence pull request that changes only
`docs/releases/v0.1.0-sandbox-evidence.json`. After review, merge it to `main` and wait
for that commit's push CI to succeed. Dispatch the `Stable release` GitHub Actions
workflow from `main` with version `v0.1.0`. The workflow rechecks the evidence, exact
candidate CI run, candidate ancestry, evidence-only diff, and release-commit CI before
publishing the multi-platform GHCR image, provenance, SBOM, Git tag, and GitHub release.

Do not create the stable tag manually. Do not dispatch the workflow when any required
assertion is false, the evidence validator fails, the candidate code changes after
testing, or a release-blocking security item remains open. Configure required reviewers
on the repository's `stable-release` environment before promotion.
