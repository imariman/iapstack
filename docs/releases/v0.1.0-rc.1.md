# v0.1.0-rc.1 Release Gate

IAPStack `v0.1.0-rc.1` is one three-provider release candidate. Apple App Store,
Google Play, and Huawei AppGallery are all release-blocking; passing only one or two
provider gates does not qualify the commit for this tag.

The release record is deliberately secret-free. Never record credentials, bearer
tokens, signed purchase bodies, purchase tokens, transaction identifiers, customer
identifiers, notification payloads, webhook secrets, or database ciphertext. IAPStack
request IDs are the only permitted correlation link to protected operational logs.

## 1. Freeze one candidate

Run every gate against one clean immutable commit:

```sh
git status --short
git rev-parse HEAD
go test -race -count=1 ./...
./deploy/e2e/run.sh
```

Wait for that commit's GitHub CI run to pass every Go, Flutter, container, and Compose
job. Copy the aggregate example without editing the example itself:

```sh
cp docs/releases/v0.1.0-rc.1-release-evidence.example.json \
  docs/releases/v0.1.0-rc.1-release-evidence.json
```

Set the top-level `commit` and CI URL to the exact candidate. Leave every result false
until it has been observed. Each provider may be executed by a different operator and
at a different UTC time, but all three must name the same release record and commit.

## 2. Execute all provider gates

- [Apple App Store sandbox gate](v0.1.0-rc.1-apple.md)
- [Google Play internal-testing gate](v0.1.0-rc.1-google-play.md)
- [Huawei AppGallery sandbox gate](v0.1.0-rc.1-huawei.md)

For every scenario, verify the provider state, IAPStack entitlement projection, and
logical webhook/event count. A successful mobile UI or HTTP response alone is not
evidence of a correct lifecycle transition.

Provider runs must use real store-managed evidence. Xcode StoreKit configuration,
locally sideloaded Google Play builds, and synthetic Huawei fixtures remain useful
automated or UI checks, but cannot satisfy the manual provider gates.

## 3. Verify the production webhook receiver

Use the exact receiver implementation and replay window intended for production:

1. Verify HMAC-SHA-256 over `<unix_timestamp>.<exact_raw_body>` and accept a valid delivery.
2. Change one raw body byte while retaining the headers and confirm rejection.
3. Submit a correctly signed event outside the timestamp tolerance and confirm rejection.
4. Replay an accepted event ID and confirm its effect is applied only once.

Mark the four top-level `webhook` assertions only after checking receiver state.

## 4. Validate and publish the candidate

Review the complete JSON before setting `no_secrets_attested`. Then run:

```sh
go run ./cmd/iapstack-release \
  docs/releases/v0.1.0-rc.1-release-evidence.json
```

The validator rejects an incomplete provider set, unknown or missing scenarios,
failed readiness checks, reused request IDs, non-UTC times, incomplete webhook
controls, unstable version formats, and placeholders.

Open an evidence-only pull request that adds exactly the completed release record.
After review, merge it to `main`, wait for push CI, and dispatch the protected
`Release` workflow with `v0.1.0-rc.1`. The workflow must publish the candidate as a
GitHub prerelease and must not update the `latest`, major, or minor container tags.

Do not publish when any required assertion is false, the candidate changes after any
provider run, a release-blocking security item remains open, or the evidence-only diff
contains another file. Fixes discovered during a provider run require a new candidate
commit and a complete rerun of every provider gate.
