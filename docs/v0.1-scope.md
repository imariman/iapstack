# IAPStack v0.1 Scope and Architecture

- Status: Revised for the three-provider release candidate
- Date: 2026-08-28
- Tracking issue: [#1](https://github.com/imariman/iapstack/issues/1)

## Purpose

IAPStack v0.1 proves that a team can self-host a secure purchase verification and entitlement service without coupling its application domain to a single store.

The release is intentionally one store-neutral vertical slice implemented across Apple App Store, Google Play, and Huawei AppGallery. A provider is not considered supported merely because its adapter or client bridge compiles: every provider must pass the same server-authority, entitlement, idempotency, notification, reconciliation, and real-store release boundaries.

## Release outcome

A developer can deploy IAPStack with PostgreSQL, configure an Apple App Store, Google Play, or Huawei AppGallery application, connect a Flutter client, verify a non-consumable purchase or subscription on the server, and ask IAPStack whether an application customer has a named entitlement.

The same deployment receives each provider's lifecycle notifications, queries authoritative store state, and removes or expires access when the underlying purchase no longer permits service.

## In scope

### Product and entitlement model

- Projects and applications with isolated store credentials
- Application-defined customers identified by a stable external customer ID
- Products mapped from store product IDs to store-neutral entitlements
- Non-consumable Apple, Google Play, and Huawei products used for lifetime access
- Auto-renewable subscriptions across all three providers, including renewal, cancellation, expiration, billing recovery states, refund, and revocation outcomes
- A current entitlement projection derived from immutable transaction and lifecycle evidence
- Restore and reconciliation flows that do not depend on the original device session

### Server capabilities

- Authenticated HTTP API for purchase submission and entitlement lookup
- Authoritative Apple App Store Server API, Google Play Android Publisher, and Huawei server API verification
- Mandatory evidence, application, product, transaction, and customer-binding consistency checks
- Durable notification inbox with idempotent processing
- Background reconciliation for uncertain, delayed, or missed lifecycle events
- Transactional outbox for signed application webhooks
- Audit trail for verification attempts and entitlement changes
- Health, readiness, structured logging, and baseline metrics endpoints

### Developer experience

- Docker Compose deployment for IAPStack and PostgreSQL
- Database migrations included with the release
- Minimal dashboard for configuration and operational inspection
- Provider-neutral and Apple, Google Play, and Huawei Flutter SDKs covering product lookup, purchase submission, restore, and entitlement lookup
- Real-device Apple sandbox, Google Play internal-testing, and Huawei sandbox release runbooks
- Stable, versioned HTTP and webhook contracts

## Explicit non-goals for v0.1

- Amazon Appstore, Samsung Galaxy Store, and providers other than Apple App Store, Google Play, and Huawei AppGallery
- Importing RevenueCat customers, receipts, or historical entitlements
- Consumable product delivery and consumption
- Remote paywall authoring, pricing experiments, or A/B testing
- Official store financial-report ingestion, proceeds, attribution, tax, or accounting features; the dashboard is limited to operational activity and an explicit revenue-availability status
- Processing payments outside official app-store billing systems
- Hosted SaaS or multi-tenant control-plane operation
- Kubernetes operators, active-active deployment, or zero-downtime regional failover
- Automatic customer alias merging beyond one stable external customer ID

These capabilities are deferred, not ruled out. The v0.1 boundaries must leave room for them without making their implementation a prerequisite for the first usable release.

## Deployable components

### API

The Go API authenticates application requests, validates input, coordinates store verification, and serves customer entitlement snapshots. It does not contain Huawei-specific HTTP or payload logic.

### Worker

The worker uses the same Go module and domain packages as the API. It processes the notification inbox, reconciliation jobs, and webhook outbox. API and worker may run as separate processes from one image.

### Dashboard

The dashboard uses only the public administrative API. It is not allowed to read PostgreSQL directly or bypass authorization rules.

### PostgreSQL

PostgreSQL is the authoritative store for configuration, customers, products, transactions, notification evidence, entitlement projections, and the inbox/outbox queues.

## Core invariants

- A store transaction belongs to exactly one configured application.
- Raw store identifiers are unique only within their store and application boundary.
- A verified purchase never grants an entitlement unless its application and product match configured catalog data.
- An entitlement is a projection of verified evidence, not a mutable flag set by a client.
- Lifetime access has no expiration but remains traceable to its source transaction.
- Subscription access has an effective interval and may remain active during a store-defined grace period.
- Duplicate client submissions and duplicate notifications produce the same final state.
- Raw signed payloads are retained for audit, but secrets and bearer credentials are never logged.

## Provider vertical slices

All providers share the same orchestration and persistence boundary. Store-specific
evidence parsing, authoritative queries, notification authentication, and lifecycle
normalization remain inside their adapters.

### Apple App Store

The Flutter companion submits StoreKit 2 signed transaction JWS evidence with a
canonical `appAccountToken`. IAPStack validates the Apple certificate chain and signed
transaction, queries the App Store Server API for authoritative subscription status,
normalizes App Store Server Notifications V2, and completes the StoreKit transaction
only after the server transaction succeeds.

### Google Play

The Flutter companion submits the purchase token and opaque account binding returned
by Google Play Billing. IAPStack queries Android Publisher, normalizes subscription and
one-time purchase state, accepts authenticated Pub/Sub RTDN pushes, and acknowledges a
completed purchase only after the entitlement and outbox transaction commits.

### Huawei AppGallery

### Initial purchase

1. The Flutter application checks Huawei IAP availability, loads products, and presents the native checkout flow.
2. Huawei returns `InAppPurchaseData` and its signature after payment.
3. The Flutter SDK submits the signed purchase data, store product ID, and IAPStack external customer ID to the API.
4. The API authenticates the application, validates request shape and size, and records a verification attempt.
5. The Huawei adapter queries the appropriate Huawei Order Service or Subscription Service endpoint using the purchase token.
6. The adapter verifies the returned signature with the configured Huawei IAP public key, checks the catalog product identity, and compares application, product ID, price, currency, and token across the client and authoritative signed evidence.
7. One PostgreSQL transaction stores the normalized store transaction, updates the entitlement projection, and appends an outbox event.
8. The API returns the resulting customer entitlement snapshot. Repeating the same request returns the same logical result.

Huawei documents the purchase token as the stable product-to-user mapping and notes that it does not change when a subscription renews. IAPStack therefore treats it as sensitive opaque data, stores up to at least 128 characters, and scopes uniqueness by store and application.

### Lifecycle notification

1. AppGallery sends a native V2 `ORDER` or `SUBSCRIPTION` callback to the application-scoped HTTPS URL.
2. IAPStack validates the outer application/version shape and verifies the signed subscription status string when present.
3. The protected purchase token must resolve to a previously verified customer, product, and product kind in the same application.
4. The worker treats the callback only as a change signal, queries Huawei's authoritative server API, and persists the resulting lifecycle projection atomically.
5. Duplicate callbacks share one inbox identity; unknown tokens retry to tolerate a callback racing initial client verification and never grant access.

1. Huawei sends a key order or subscription event to the configured HTTPS endpoint.
2. IAPStack authenticates and validates the notification, then durably inserts it into the inbox before returning success.
3. Duplicate deliveries are accepted but collapse onto the same inbox identity.
4. The worker queries Huawei for current authoritative state instead of trusting the notification as a complete state snapshot.
5. The worker verifies the response, appends new lifecycle evidence, and recomputes the entitlement.
6. A changed entitlement creates a signed outbox webhook for the application backend.

Huawei retries subscription notifications when the recipient does not return HTTP 200. This makes durable-before-acknowledge processing and idempotency mandatory rather than optional optimizations.

### Restore and reconciliation

The client can resubmit active purchases returned by the Huawei SDK. IAPStack verifies every item and attaches valid evidence to the authenticated external customer. A scheduled worker also rechecks subscriptions whose state is time-sensitive, uncertain, or near expiration.

## Security boundary

- Client purchase data is evidence, not authority.
- Every grant requires server-side signature verification and catalog consistency checks.
- Store credentials are supplied through deployment secrets and encrypted when persisted.
- Public API keys are stored as one-way hashes; administrative credentials are separate.
- Notification and application webhooks have replay protection and bounded timestamp tolerance.
- All state transitions use database transactions and deterministic idempotency keys.
- Network clients use explicit timeouts, bounded responses, redacted errors, and retry policies with jitter.
- Cryptographic algorithms use maintained standard-library or audited dependencies; IAPStack does not implement cryptographic primitives.

## Quality gates

A `v0.1.0-rc.1` release candidate must pass:

- Formatting, static analysis, race-enabled unit tests, and integration tests in CI
- PostgreSQL migration up/down tests from an empty database
- Real-provider tests for Apple App Store, Google Play, and Huawei AppGallery covering non-consumable purchase, restore, subscription lifecycle, refund/revocation, negative bindings, duplicate delivery, and missed-notification reconciliation
- One schema-v2 secret-free release record containing all three provider gates for the exact same candidate commit and successful CI run
- Contract compatibility tests for the Flutter SDK and dashboard
- Threat-model review for purchase verification, notification replay, credential storage, and customer identity binding
- Backup and restore rehearsal for PostgreSQL
- Documented upgrade and rollback procedure

## Delivery sequence

1. Go module, configuration, process lifecycle, and CI
2. Core domain contracts and store adapter boundary
3. PostgreSQL persistence, migrations, inbox, and outbox
4. Apple, Google Play, and Huawei authentication and purchase verification
5. Entitlement projection and lifecycle reconciliation
6. Public API, provider-neutral and provider-specific Flutter SDKs, and real-store harnesses
7. Dashboard and operational tooling
8. Hardened Docker Compose release
